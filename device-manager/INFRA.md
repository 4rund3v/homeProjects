# Infrastructure — Docker Compose, Kubernetes, Helm, Terraform

This file describes how the system is packaged and deployed, from a laptop to a production cluster. It is a companion to DESIGN.md, which explains why each choice was made.

---

## The Deployment Progression

The system moves through four levels of packaging, each a superset of the last:

1. **Docker Compose** — everything on one host, for local development.
2. **Raw Kubernetes manifests** — a learning reference showing each resource explicitly.
3. **Helm chart** — the real packaging. One chart, three environment configurations.
4. **Terraform** — the substrate beneath all of it: the cluster, the network, DNS, certificates, secrets, and monitoring.

You develop against the first, learn from the second, deploy with the third, and provision the fourth.

---

## Docker Compose — Local Development

**Purpose:** run every dependency on one machine with no cluster required.

**Services:**
- PostgreSQL with a named volume for persistence and a health check based on the native readiness command.
- Redis for the cache, the broker, and the pub/sub bridge. Persistence disabled for the cache role in development; the broker queue is regenerated by re-triggering traces.
- Kafka in KRaft mode, single broker, with the three topics auto-created on startup.
- Keycloak with a pre-seeded realm, client, groups, and protocol mappers for the scope claim.
- The observability agent, receiving traces on the trace port and metrics on the stats port. Runs fully locally; no cloud account needed.

**Why health checks matter even locally:** the application's startup sequence waits for dependencies. Without a health check, the backend starts before Postgres is accepting connections and fails on the first migration. The check turns a race condition into a deterministic wait.

**Volumes:** Postgres gets a named volume so device history survives a restart. Kafka gets one so the event log survives. Redis does not — losing the cache is a cache miss, and losing the broker queue is a re-triggered trace.

## Kubernetes Concepts Used

Before the manifests make sense, the resource types and why each is chosen:

**Deployment** — for stateless processes. The HTTP handler, the WebSocket holder, the Celery worker, the Go service, the stream processor, and the frontend are all Deployments. Any replica can serve any request.

**StatefulSet** — for the database. StatefulSets give stable network identity and stable storage, which a database needs. A Deployment would work for a single replica, but the moment you want a replica set with persistent identity, the StatefulSet is the correct primitive.

**Service** — stable in-cluster addressing. ClusterIP for internal services. The ingress routes external traffic in; Services route it onward.

**PersistentVolumeClaim** — durable storage for the database. The claim survives pod restarts, so device history is never lost to a reschedule.

**ConfigMap** — non-secret configuration injected as environment variables or files.

**Secret** — sensitive configuration. In development, a Kubernetes Secret. In production, a reference to the external secret manager.

**Ingress** — external HTTP and WebSocket routing with TLS termination. The ingress holds the certificates; the applications behind it speak plain HTTP internally.

**HorizontalPodAutoscaler** — scales the stateless HTTP handler on CPU utilization.

**PodDisruptionBudget** — protects the WebSocket holder from being fully evicted during node drains and rolling updates.

**NetworkPolicy** — the in-cluster firewall. Restricts which pods can reach which ports, so a compromised pod in one namespace cannot reach the database directly.

**Certificate resources** — automatic issuance and renewal from the internal authority and the public issuer.

## The Helm Chart

**Purpose:** one package that deploys the entire system, configurable per environment.

**Structure:**
- A chart metadata file declaring the name, version, and dependencies.
- Shared default values applying to every environment.
- Three values files overriding the defaults for development, staging, and production.
- A helpers template defining shared labels and computed names.
- One template per deployment, plus one per service.
- Templates for the autoscaler, the disruption budget, the network policies, the secrets, and the certificates.

**What differs between environments:**
- Replica counts. Development runs single replicas; production runs multiple.
- Resource requests and limits. Development is minimal; production is sized for load.
- Storage size and class. Development uses the local-path class; production uses a replicated class.
- Ingress hostname and certificate issuer. Development uses a local hostname and the internal authority; production uses a real domain and the public issuer.
- Log level and debug flags. Development is verbose; production is measured.

**What never differs:** the templates themselves. The same template produces a development pod and a production pod; only the values change. That is the discipline that makes environments comparable — a staging failure means something real, because staging and production differ only in scale.

**Dependencies:** the database, cache, and broker use published charts as subcharts rather than hand-written templates. Writing your own PostgreSQL StatefulSet is a learning exercise you do once; running a maintained one is what production does. The dependency versions are pinned.

## Templates That Deserve Explanation

**The HTTP deployment** carries a liveness probe on a dedicated liveness path and a readiness probe on a readiness path. The liveness probe checks only that the process is alive — if it fails, the container restarts. The readiness probe checks that the process can actually serve, verifying the database, cache, and broker — if it fails, the pod is removed from the Service's endpoints but is not restarted, because restarting would not fix a dependency outage. Getting this distinction wrong is a common cause of cascading failures: a readiness problem misconfigured as liveness causes a restart loop that makes the outage worse.

The HTTP deployment also carries a pre-shutdown hook that sleeps briefly before the container stops. This gives the cluster time to remove the pod from the load balancer's rotation before the process begins refusing connections, which eliminates the dropped requests that otherwise accompany every deploy.

**The WebSocket deployment** does not autoscale. Scaling it would drop connections, because each replica holds its own set. Instead it runs a fixed replica count and carries a disruption budget allowing zero unavailable replicas, so a node drain or rolling update cannot evict every connection-holding pod at once. Its termination grace period is long, so connections drain before the process is killed.

**The Celery deployment** scales on queue depth rather than CPU, because the workload is I/O-bound — waiting on the scan, waiting on the database — not compute-bound.

**The Go service deployment** runs one replica per node. It scans the local network, so it must be co-located with the network segment it scans. It cannot be scaled horizontally behind a load balancer, because each instance sees a different network. This is a case where the scaling model of a stateless web service does not apply, and recognizing that is part of the design.

**The network policy set** encodes the trust boundaries: only the ingress controller reaches the HTTP handler on its port; only the Celery worker reaches the Go service on its port; only the application pods reach the database. These policies are a second layer behind mutual TLS, not a replacement for it — they authenticate location, the certificates authenticate identity, and defense in depth uses both.

## Terraform Structure

**Purpose:** provision everything beneath and around the cluster, reproducibly.

**Modules:**
- **Cluster** — provisions the Kubernetes cluster, either a lightweight single-node cluster for on-premises or a managed cluster in the cloud. Outputs the credentials the Helm releases use.
- **Networking** — the private network, subnets, routing, firewall rules, and DNS. The only externally exposed port is the HTTPS ingress; everything else is internal.
- **TLS** — the public certificate issuer for the browser-facing domain and the internal authority for service-to-service certificates. Both auto-renew.
- **Secrets** — the secret manager namespace holding the database password, the token signing key, the broker credentials, and the observability API key. Injected at runtime; never in version control, never in a container image, never in Helm values.
- **Monitoring** — the alerting rules and dashboards defined as code. Each monitor has a query, a threshold, and a message linking to its runbook.

**Why monitoring lives in Terraform:** because an alerting rule change should be reviewed like any other change. A threshold adjusted in a web console is invisible, unauditable, and untraceable. A threshold adjusted in a pull request has a reviewer, a rationale, and a history. This is the same argument as infrastructure-as-code generally, applied to the part of the system that tells you when things are broken.

**State management:** Terraform state is stored remotely with locking, so two engineers cannot apply concurrently and corrupt it. The state file contains sensitive values, so its backend is encrypted and access-controlled.

**The lifecycle:** plan shows what will change; apply makes it change; destroy removes everything. The destroy command is not just cleanup — it is the proof that the infrastructure is fully reproducible from code. If destroy leaves something behind, something was created outside the code, and that something will eventually surprise someone.

## Secrets Management

**The rule:** no secret is ever committed, baked into an image, or placed in a Helm values file that is committed.

**Development:** a local dotenv file, gitignored, with a committed example showing every variable and a safe default.

**Cluster:** Kubernetes Secrets for the simple cases, and an external secret manager for production. The application reads secrets at startup through a driver or a sidecar, so the values exist only in memory in the running process.

**What counts as a secret:** the database password, the token signing key, the broker credentials, the observability API key, the OAuth client secret, and the certificate authority private key. The certificate authority key in particular never leaves its provisioning directory and is never committed — losing it means every issued certificate must be re-issued, and an attacker obtaining it means they can mint certificates for any service.

## Networking

**Externally exposed:** HTTPS on the ingress, nothing else.

**Internally:** pods communicate over Services on cluster-internal addresses. The database, cache, and broker are not reachable from outside the cluster at all.

**The ingress** terminates TLS and proxies two kinds of traffic: plain HTTP requests to the API, and WebSocket upgrades to the connection holder. The WebSocket proxying requires specific upgrade and connection headers; without them the proxy treats the handshake as an ordinary request and the connection fails. This is the single most common misconfiguration in WebSocket deployments.

**DNS:** a real hostname in production, managed by the networking module, pointing at the ingress. A local hostname in development, added to the hosts file, pointing at the cluster node.

## What This Buys You

The compose file lets you develop without a cluster. The raw manifests teach you what Helm is generating on your behalf. The Helm chart lets you deploy the identical system to three environments with three values files. And Terraform proves that everything beneath the chart is reproducible from code. Together they are the difference between a project that runs on your machine and a system that runs in an organization.
